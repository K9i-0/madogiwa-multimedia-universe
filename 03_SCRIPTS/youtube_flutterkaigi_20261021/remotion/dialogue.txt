# scene
Z|game_night|その3Dモデルは、Flutterでどう動かしているのだ？　Unityを埋め込んでいるのだ？
M|scene|いいえ、これはFlutter Sceneというパッケージを使っているの。
Z|scene|何なのだ、それ？
M|v9_ui_build|その仕組みを知るために、まずは普段のFlutterが、コードから画面を作る流れを見てみましょう。
M|v9_ui_build|例えば、アイコンの下に文字が並ぶ画面。ColumnにIconとTextを入れると、縦に並べたいという画面の構成を表せるわ。
Z|v9_ui_build|でも、Widgetを書いただけでは、まだ画面の色は塗られていないのだ？
M|v9_ui_layout|そう。まず構成を組み立てて、それをもとに、大きさと位置を決める。これがレイアウトよ。画面のどこに、どれだけの場所を使って置くかを決めるの。
M|v9_ui_layout|この配置や、次の描画命令を作る仕事を担うのがRenderObject。Widgetは画面の構成を記述し、実際の配置と描画には、こうした別の仕組みが働いているわ。
Z|v9_ui_paint|配置が決まったら、その場所に絵を描くのだな。
M|v9_ui_paint|ええ。ペイントの段階で、ここに形を描く、ここに文字を描く、という描画命令を記録するの。必要なレイヤーを組み合わせて、エンジンに渡すわ。
M|v9_ui_engine|その先でImpellerなどの描画エンジンがGPUへ仕事を渡し、画面のピクセルを作る。普段のFlutterも、最初からGPUを使っているのよ。
Z|v9_ui_engine|あれ？　もうGPUを使っているなら、Flutter GPUを追加する意味は何なのだ？
M|v9_gpu_door|違うのは、Dartから何を指定できるかよ。普段のUIでは、文字や図形を描くための高いレベルの命令を使う。Flutter GPUでは、頂点データやシェーダー、描画先を、より低いレベルで組み立てられるの。
Z|v9_gpu_door|Impellerは2D専用だから、3D用の別エンジンに取り替える、という話ではないのだ？
M|v9_gpu_door|そうではないわ。Impellerには、低レベルの描画基盤と、その上でUIを描く仕組みがあるの。Flutter GPUは、その描画基盤をDart側から利用できるようにしたAPIよ。
Z|v9_triangle|低いレベルで組み立てるって、実際には何をするのだ？
M|v9_triangle|三角形を一枚描く例なら、まず三つの頂点のデータを用意する。頂点シェーダーで座標を変換して、画面のどこに見えるかを決めるわ。
M|v9_triangle|続いて、ラスタライズで三角形が画面のどこを覆うかを求め、フラグメントシェーダーで色などを計算するの。これが、頂点から画面の絵を作る基本の流れね。
Z|v9_depth|3Dモデルは、その三角形がたくさん集まったものなのだな。でも、手前と奥はどうするのだ？
M|v9_depth|カメラから見た座標への変換と、奥行きを比べる深度テストを使うわ。手前の面が奥の面を隠す、といった処理も、描画の設定として扱えるの。
Z|v9_scene_layer|ちくわを一本表示するために、毎回そこまで書くのは大変そうなのだ。
M|v9_scene_layer|そこでFlutter Sceneよ。モデルの読み込み、カメラ、材質、ライト、アニメーションといった、3Dで使う仕組みをまとめているわ。
M|v9_scene_layer|ゲーム側はモデルをどこに置くか、カメラをどこへ向けるかを指定する。Flutter Sceneが、それをFlutter GPUの描画処理へつなぐの。
Z|v9_scene_layer|普段はWidgetに画面づくりを任せるように、3Dの描画はSceneに任せられるのだな。
M|v9_scene_layer|ええ。ネイティブではFlutter Scene、Flutter GPU、Impellerの描画基盤という関係。Flutter GPUそのものが、ゲームのルールや操作まで作ってくれるわけではないわ。
Z|stable|試すには、Flutterの開発版が必要なのだ？
M|stable|Stable版で使えるわ。このゲームはFlutter 3.47.8。Flutter Sceneの現在の案内では、3.47以降が対象よ。
M|stable|ただし、ネイティブではImpellerとFlutter GPUの有効化が必要よ。SDKがStable版でも、Flutter GPUのAPIの安定性まで保証されるわけではないの。

# mcp
Z|mcp_overview|コードを読ませる以外に、何をつなぐのだ？
M|mcp_overview|この開発では、Dart MCP、Marionette MCP、mobile MCPを使っているわ。MCPは、AIが外部のツールを呼び出すための共通の接続方式ね。
M|v10_usage|先に使い分けを整理するわ。普段の開発と動作確認は、デバッグビルドでMarionetteを使う。今回の日常的な操作や状態確認は、ほとんどこれで足りているの。
M|v10_usage|実機でパフォーマンスを調整するときは、mobile MCPで端末を操作する。性能の測定は、別にprofileビルドと計測ログで行うわ。
Z|v10_inside|どちらもアプリを操作するのに、何が違うのだ？
M|v10_inside|MarionetteはFlutterアプリの中につながるの。Widgetの文字やキーで操作対象を指定できるから、画面の画像だけを頼りに探す必要がなくて、開発中の確認を効率よく進められるわ。
M|v10_outside|mobile MCPは、端末側の仕組みで外から操作するの。Flutter専用の接続をアプリに入れなくても、タップや画面取得ができるわ。
Z|v10_limits|では、Marionetteは実機では使えないのだ？
M|v10_limits|実機でも使えるわ。ただ、このゲームではMarionetteをdebugのときだけ有効にしているの。VM Serviceへの接続が必要で、releaseビルドでは使えない、という制約もあるわ。
M|v10_usage|だから今回は、開発中はMarionetteを中心に使い、実機の性能調整ではmobile MCPで操作を補う。このプロジェクトでの使い分けとして覚えてね。
M|dart_mcp|まずDart MCP。DartとFlutterの公式の開発ツールを、AIから呼び出せるようにするサーバーよ。
Z|dart_mcp|普段、IDEで押しているボタンを、AIも押せる感じなのだ？
M|dart_mcp|ええ。このリポジトリでは、アプリの起動、hot reload、Widgetの調査、実行時エラーの取得などを有効にしているわ。
M|dart_bridge|実行中のアプリとは、Dart Tooling Daemonなどの開発用の接続を使ってやり取りするの。返ってきた情報を、次の修正に使えるわ。
Z|reload_loop|毎回ぼくが起動して、エラーをコピペしなくてもいいのだな。
M|reload_loop|コードを直して、hot reloadして、結果を確かめる。このFlutterの短い反復を、AIの作業にも組み込めるの。
Z|v10_inside|起動した後の操作が、さっきのMarionetteなのだな。
M|v10_inside|ええ。アプリに組み込んだMarionetteBindingが、操作や調査の窓口を用意するの。AIのツール呼び出しが、Dart VM Serviceを通って、その窓口へ届く仕組みよ。
M|widget_actions|Widgetの情報を調べ、文字やキーを手がかりにタップや入力ができるの。画面の画像やログも確認できるわ。
Z|game_inspect|では、落ちてくるちくわも、Widgetを探せば見つかるのだ？
M|game_inspect|そこが3Dゲームの工夫どころよ。ちくわは3Dシーンの中にあって、一個ずつWidgetになっているわけではないの。
M|custom_extension|だから、このゲーム専用の拡張を登録したわ。得点や座標、落下物の状態を、構造化したデータとして取り出せるの。
Z|custom_extension|見た目だけで、取れたはずだ、と推測しなくていいのだな。
M|deterministic|操作用の拡張では、乱数の条件をそろえ、入力を渡して一定時間だけ進められるわ。同じ条件で、キャッチ判定やカメラの向きを調べられるの。
Z|deterministic|ちくわの再現実験なのだ。
# balance
Z|v9_balance_target|同じ条件で何度も動かせるなら、ゲームの難しさもAIに調整してもらえるのだ？
M|v9_balance_target|ええ。まず、来場者の目標合格率を決めたわ。福ギュンは90パーセント、おだてつは50パーセント、そば屋は5パーセント。気軽に遊べるものから、難しいものまで分けたの。
Z|v9_balance_bot|そば屋、ビールへの執念を試しすぎなのだ。AIが200回くらい画面を見ながら遊ぶのだ？
M|v9_balance_bot|この検証では、AIが作ったプログラムで自動プレイするの。反応時間と狙いの誤差を変えた200体のボットに、実際のゲームロジックを動かしてもらうわ。
M|v9_balance_bot|反応は0.2秒から0.5秒。狙いも少しずれる。完璧な操作だけでなく、操作のばらつきを入れて、配置ごとの合格率や満点の割合を比べるの。
Z|v9_balance_limit|じゃあ、ボットの半分が合格すれば、お客さんも半分が合格するのだ？
M|v9_balance_limit|そこは同じではないわ。ボットは落下物の種類や着地位置を最初から分かっている。人がカメラを回して見分ける手間までは再現していないの。
M|v9_balance_limit|だからボットの結果は、候補を比較する目安として使う。来場者の目標合格率を達成した、という実測結果にはできないわ。
Z|v9_balance_human|最後は、ちゃんと人間が遊ぶのだな。
M|v9_balance_human|ええ。実機で遊ぶと、取れたように見えるのに外れる場面があった。そこで、当たりだけ判定の幅を広げて、着地後にも0.15秒の猶予を入れたの。
M|v9_balance_human|その後、おだてつはもう少し難しくていいとなった。配置の候補を再検証して、ボットの合格率は約80パーセントを目安に、77パーセントの配置を採用したわ。
Z|v9_balance_loop|AIで候補を絞って、人の感覚で直して、また検証するのだ。
M|v9_balance_loop|そう。さらに、入力を細かく探索するTASで、満点を取れることも確認したわ。難しいけれど不可能ではない、という設計を支える検証ね。
M|v9_balance_loop|数字で比較できる部分は自動化し、見分けやすさや操作の気持ちよさは人が確かめる。その往復で、ブース向けに仕上げているの。

# performance
Z|game_night|その実機検証で、何が見つかったのだ？
M|performance|描画の待ち時間とメモリ使用量に問題が見つかって、改善したわ。
Z|performance|3Dだから、ポリゴンを減らしたのだ？
M|lights|それだけではないの。Androidでは、変わっていないライトのデータまで毎フレームGPUへ送る処理が、待ち時間につながっていたの。
M|fps|そこを改善する上流の修正を取り込んだコミットには、Pixel 7aで約30fpsから約60fpsになった記録があるわ。
Z|fps|見た目を削る前に、余計な更新を減らせたのだな。
M|textures|iPhoneでは、キャラクターの4096四方のテクスチャを、ゲーム用に最大2048へ縮小したわ。
M|memory|ライブラリの更新と素材の縮小を含む改善後は、iPhone 14のロード時ピークメモリが、約1.9GBから約0.74GBに下がった記録があるわ。
Z|textures|画面の中では小さく見える人に、大きなテクスチャを持たせていたのだ。
M|textures|元の制作素材をそのまま使うのではなく、ゲームでの見え方に合わせた素材を用意するのも大切ね。
Z|performance|Flutterのコードだけ見ていても、終わらないのだな。
M|performance|Dartの処理、描画ライブラリ、3D素材。どこが原因なのかを測って、必要なところを直していくの。
