# scene
M|scene|まずはflutter_scene。Flutterで3Dを描くためのパッケージよ。このアプリでは本家をフォークして、固定したコミットを参照しているの。
Z|scene|フォークしているのだ？
M|scene|本家の更新を取り込みながら、アニメーションの切り替えまわりの小さな修正を3つ載せているわ。
Z|scene|で、そもそも、どうやってFlutterで3Dを描くのだ？
M|v9_ui_build|その仕組みを知るために、まずは普段のFlutterが、コードから画面を作る流れを見てみましょう。
M|v9_ui_build|例えば、アイコンの下に文字が並ぶ画面。ColumnにIconとTextを入れると、縦に並べたいという画面の構成を表せるわ。
Z|v9_ui_build|でも、Widgetを書いただけでは、まだ画面の色は塗られていないのだ？
M|v11_trees|そう。Flutterは、Widgetのツリーをもとに、Elementのツリーを作るの。Elementは、ツリーのある場所に置かれたWidgetの実体で、フレームをまたいで使い回されるわ。
M|v11_trees|そして、配置や描画にかかわるElementは、RenderObjectを持つ。これがRenderObjectのツリーよ。
Z|v11_trees|設計図のWidget、それを管理するElement、実際に描くRenderObject。3本のツリーがあるのだな。
M|v9_ui_layout|ええ。レイアウトでは、RenderObjectのツリーを上からたどって、大きさと位置を決めるの。
M|v9_ui_layout|親は子に大きさの制約を渡し、子はその範囲で自分の大きさを返す。これで、画面のどこに、どれだけの場所を使って置くかが決まるわ。
Z|v9_ui_paint|配置が決まったら、その場所に絵を描くのだな。
M|v9_ui_paint|ええ。ペイントの段階で、ここに形を描く、ここに文字を描く、という描画命令を記録するの。必要なレイヤーを組み合わせて、エンジンに渡すわ。
M|v9_ui_engine|その先でImpellerなどの描画エンジンがGPUへ仕事を渡し、画面のピクセルを作る。普段のFlutterも、最初からGPUを使っているのよ。
Z|v9_ui_engine|あれ？　もうGPUを使っているなら、Flutter GPUを追加する意味は何なのだ？
M|v9_gpu_door|違うのは、Dartから何を指定できるかよ。普段のUIでは、文字や図形を描くための高いレベルの命令を使う。Flutter GPUでは、頂点データやシェーダー、描画先を、より低いレベルで組み立てられるの。
Z|v9_gpu_door|Impellerは2D専用だから、3D用の別エンジンに取り替える、という話ではないのだ？
M|v9_gpu_door|そうではないわ。Impellerには、低レベルの描画基盤と、その上でUIを描く仕組みがあるの。Flutter GPUは、その描画基盤をDart側から利用できるようにしたAPIよ。
Z|v9_triangle|低いレベルで組み立てるって、実際には何をするのだ？
M|v9_triangle|三角形を一枚描く例なら、まず三つの頂点のデータを用意する。頂点シェーダーで座標を変換して、画面のどこに見えるかを決めるわ。
M|v9_triangle|続いて、ラスタライズで三角形が画面のどこを覆うかを求め、フラグメントシェーダーで色などを計算するの。これが、頂点から画面の絵を作る基本の流れね。
Z|v13_shader|そういえば、Flutter GPUより前にも、シェーダーのファイルを読み込むFragmentShaderがあったのだ。今のフラグメントシェーダーとは、何が違うのだ？
M|v13_shader|色を計算する処理という点は同じ。でも、dart:uiのFragmentShaderとFlutter GPUでは、アプリから指定できる範囲が違うの。
M|v13_shader|FragmentShaderは、例えばCanvasで描く四角形の塗り方を、自分のシェーダーに変える仕組みよ。波模様や、画像をゆがめる表現などに使えるわ。
Z|v13_shader|いつもの描画に、色の計算を差し込む感じなのだな。
M|v13_shader|そう。そのAPIからは、自分の頂点シェーダーや深度テストを指定できない。一方、Flutter GPUでは、頂点データから、頂点とフラグメントの両方のシェーダー、深度の設定まで組み立てられるの。
Z|v13_shader|FragmentShaderは、もう古いから置き換える、という話ではないのだ？
M|v13_shader|ええ。塗り方や画像の効果を変えたいならFragmentShader。今回のように、モデルの頂点や奥行きを扱う描画を組み立てたいならFlutter GPU。目的で使い分けるのよ。
Z|v9_depth|頂点の話につながったのだ。3Dモデルは、その三角形がたくさん集まったものなのだな。でも、手前と奥はどうするのだ？
M|v9_depth|カメラから見た座標への変換と、奥行きを比べる深度テストを使うわ。手前の面が奥の面を隠す、といった処理も、描画の設定として扱えるの。
Z|v9_scene_layer|ちくわを一本表示するために、毎回そこまで書くのは大変そうなのだ。
M|v9_scene_layer|そこでFlutter Sceneよ。モデルの読み込み、カメラ、材質、ライト、アニメーションといった、3Dで使う仕組みをまとめているわ。
M|v9_scene_layer|ゲーム側はモデルをどこに置くか、カメラをどこへ向けるかを指定する。Flutter Sceneが、それをFlutter GPUの描画処理へつなぐの。
Z|v9_scene_layer|普段はWidgetに画面づくりを任せるように、3Dの描画はSceneに任せられるのだな。
M|v9_scene_layer|ええ。このゲームをiOSやAndroidのアプリとして動かす場合は、Flutter Scene、Flutter GPU、Impellerの描画基盤という関係よ。Flutter GPUそのものが、ゲームのルールや操作まで作ってくれるわけではないわ。
Z|stable|試すには、Flutterの開発版が必要なのだ？
M|stable|Stable版で使えるわ。このゲームはFlutter 3.47.8。Flutter Sceneの現在の案内では、3.47以降が対象よ。
M|stable|ImpellerはStable版の標準の描画エンジンだから、そのままでいい。追加で必要なのは、Info.plistやAndroidManifestで、Flutter GPUを有効にする設定よ。
M|stable|ただし、SDKがStable版でも、Flutter GPUのAPIの安定性まで保証されるわけではないの。

# implementation
Z|ui|じゃあ、いつものWidgetはどこにいるのだ？
M|ui|キャラクター選択や、得点、残り時間、設定画面はFlutterのUIよ。3Dの描画と組み合わせているの。
M|logic|ゲームのルールもDartで書いているわ。端末の傾きを移動入力にして、キャラクターを動かす。落下物との位置関係を見て、キャッチしたら得点を更新するの。
Z|v11_tilt|その端末の傾きは、どうやって取っているのだ？

M|v11_tilt|ごく小さな傾きは無視して、約14度で最高速度。遊び始めたときの持ち方を基準にするから、少し斜めに持っていても大丈夫よ。
Z|v11_tilt|シミュレーターでは、端末を傾けられないのだ。
M|v11_tilt|シミュレーターでは矢印キーで代わりに操作できるわ。AIで確かめるときは、あとで紹介する専用の拡張から、傾きの値を直接渡すの。

M|game_odatetsu|それから今の標準操作は、画面で傾けた方向を、鉄骨に沿った移動へ変換しているの。斜めから見ると、前後の傾きも移動に反映されるわ。

# mcp
Z|mcp_overview|コードを読ませる以外に、何をつなぐのだ？
M|mcp_overview|この開発では、Dart MCPとMarionette MCPを使っているわ。MCPは、AIが外部のツールを呼び出すための共通の接続方式ね。
M|dart_mcp|まずDart MCP。DartとFlutterの公式の開発ツールを、AIから呼び出せるようにするサーバーよ。
Z|dart_mcp|普段、IDEで押しているボタンを、AIも押せる感じなのだ？
M|dart_mcp|ええ。このリポジトリでは、アプリの起動、hot reload、Widgetの調査、実行時エラーの取得などを有効にしているわ。
M|dart_bridge|実行中のアプリとは、Dart Tooling Daemonなどの開発用の接続を使ってやり取りするの。返ってきた情報を、次の修正に使えるわ。
Z|reload_loop|毎回ぼくが起動して、エラーをコピペしなくてもいいのだな。
M|reload_loop|コードを直して、hot reloadして、結果を確かめる。このFlutterの短い反復を、AIの作業にも組み込めるの。
Z|v11_marionette_pkg|起動した後に、画面を操作するのはどうするのだ？
M|v11_marionette_pkg|そこで、pubspecにあったmarionette_flutterの出番よ。開発用の道具なのに、dev_dependenciesではなく、普通の依存に入っているの。
Z|v11_marionette_pkg|開発用なのに、アプリ本体に入れていいのだ？
M|v11_marionette_pkg|main関数で専用のBindingを初期化するからよ。releaseビルドでは、コンパイル時の定数で分岐して、使わないようにしているわ。
M|v10_inside|このMarionetteBindingが、アプリの中に操作や調査の窓口を用意するの。AIのツール呼び出しが、Dart VM Serviceを通って、その窓口へ届く仕組みよ。
M|widget_actions|Widgetの文字やキーで操作対象を指定できるから、画面の画像だけを頼りに探す必要がないの。画面の画像やログも確認できるわ。
Z|game_inspect|では、落ちてくるちくわも、Widgetを探せば見つかるのだ？
M|game_inspect|そこが3Dゲームの工夫どころよ。ちくわは3Dシーンの中にあって、一個ずつWidgetになっているわけではないの。
M|custom_extension|だから、このゲーム専用の拡張を登録したわ。得点や座標、落下物の状態を、構造化したデータとして取り出せるの。
Z|custom_extension|見た目だけで、取れたはずだ、と推測しなくていいのだな。
M|deterministic|操作用の拡張では、乱数の条件をそろえ、傾きの入力を渡して一定時間だけ進められるわ。同じ条件で、キャッチ判定やカメラの向きを調べられるの。
Z|deterministic|ちくわの再現実験なのだ。
Z|v11_modes|でも、Dart VM Serviceが必要なら、Marionetteが使えるのはデバッグビルドだけなのだ？
M|v11_modes|profileビルドでも使えるわ。使えないのは、VM Serviceがないreleaseビルドだけ。profileではhot reloadは使えないけれど、同じ場面をMarionetteで再現しながら、性能を測れるの。
M|v11_modes|ちなみに開発者は、Marionetteはprofileビルドでは使えないと思い込んで、実機の検証ではmobile MCPと使い分けていたわ。
Z|v11_modes|さすが窓際族なのだ。
M|v11_modes|この解説動画の裏取りで気づいて、profileビルドでも実際に操作できることを確かめたわ。

M|v9_balance_limit|そこは同じではないわ。ボットは落下物の種類や着地位置を最初から分かっている。人がカメラを回して見分ける手間までは再現していないの。

# performance
Z|game_night|その実機検証で、何が見つかったのだ？
M|performance|描画の待ち時間とメモリ使用量に問題が見つかって、改善したわ。
Z|performance|3Dだから、ポリゴンを減らしたのだ？
M|lights|それだけではないの。Androidでは、変わっていないライトのデータまで毎フレームGPUへ送る処理が、待ち時間につながっていたの。
M|fps|そこを改善する上流の修正を取り込むと、Pixel 7aは約30fpsから約60fpsになったわ。ただしこれは、端末の性能を固定するモードで測った値よ。
Z|v11_fps_mode|普段のモードだと、どうなのだ？
M|v11_fps_mode|普段の電力モードで遊ぶと、画面の更新は約46から50fps。しかも、3Dが描き直されるのは1秒に約20回だったの。
Z|v11_fps_mode|fpsと、3Dの描き直しの回数が違うのだ？
M|v11_frames|Flutter Sceneは、3Dの描画命令をUIスレッドで組み立てる。GPUが前のフレームを描き終わっていないと、新しく描かずに、前の画像をもう一度出すの。
M|v11_frames|Pixel 7aの普段のモードでは、その組み立てが1フレームに収まらず、3フレームに1回しか3Dを描けなかった。だから、fpsの数字だけでなく、描き直しの回数も数えるのよ。
Z|v11_frames|60fpsと書いてあっても、油断できないのだ。
M|v11_frames|遊ぶのに支障はないから、今回はここまでにしているわ。次に直すなら、影やライトの計算を軽くするところからね。
M|textures|iPhoneでは、上流の修正を取り込んだら、今度はメモリが増えて、読み込み中にアプリが強制終了したの。
Z|textures|直したら、別のところが壊れたのだ。
M|textures|原因の一つは、キャラクターの4096四方のテクスチャ。ゲーム用に、最大2048へ縮小した素材を用意したわ。
M|memory|その結果、iPhone 14の読み込み時のピークメモリは、改善前の約1.9GBから、約0.74GBまで下がったわ。
Z|textures|画面の中では小さく見える人に、大きなテクスチャを持たせていたのだ。
M|textures|元の制作素材をそのまま使うのではなく、ゲームでの見え方に合わせた素材を用意するのも大切ね。
Z|performance|Flutterのコードだけ見ていても、終わらないのだな。
M|performance|Dartの処理、描画ライブラリ、3D素材。どこが原因なのかを測って、必要なところを直していくの。
